# 全新外卖系统实施计划

## 原则与当前阶段

以苍穹外卖作为业务参考，重新设计完整的外卖系统。没有历史用户、历史业务数据、旧 API 或旧前端
需要兼容。源码参考版本为 [f4013148](https://github.com/Danyhug/heima_sky_take_out/tree/f4013148cdd168c7af3e311dbb96b71cc532ff6b)。
业务盘点见 [参考能力清单](REFERENCE_CAPABILITIES.md)，本系统架构见 [架构决策](ARCHITECTURE.md)。

P0/P1 已完成，P1 复查见 [验收记录](P1_ACCEPTANCE.md)。P2 已实现商品目录与门店营业，
范围和验证见 [P2 契约](P2_CONTRACT.md)。P3 顾客与购物车已实现，见 [P3 契约](P3_CONTRACT.md)。
P4 已实现完整未支付订单生命周期，见 [P4 契约](P4_CONTRACT.md)。P5 后端支付／履约与沙箱交易闭环已实现，见 [P5 契约](P5_CONTRACT.md)。P6 通知、鉴权长连接与经营统计已实现，见 [P6 契约](P6_CONTRACT.md)。P7 尚未实施。
顾客端确定使用 Flutter App，后端已接入支付宝沙箱；移动端 SDK 真机联调留待 P7。
详细边界见 [移动端与支付决策](MOBILE_PAYMENT_DECISION.md)。
每个阶段按实际用例纵向交付领域行为、持久化、API、测试和文档；不先批量堆砌空 Service/Mapper。

## 技术基线

- JDK 25、Spring Boot 4.1.1、Spring Modulith 2.1.1，单一应用和部署产物。
- Spring Data JPA/Hibernate 负责 ORM，Flyway 负责版本化 DDL；生产业务代码不依赖 JDBC API。
- PostgreSQL、Redis、RustFS 使用本机统一的 Podman Compose 与 systemd 服务。
- Spring Security、BCrypt、持久化会话、Redis 限流；DTO 边界统一 RFC 9457 错误。
- Guava 与 Commons Lang3 在应用/适配层简化通用处理，领域保持纯 Java。
- 中文注释、Google Java Format、Checkstyle 和完整测试作为提交门禁。

## 业务边界

| 模块 | 业务职责 | 主要模型 |
| --- | --- | --- |
| identity | 员工身份、权限、账号生命周期 | EmployeeAccount、Session、认证策略 |
| customer | 顾客资料、收货地址和默认地址 | Customer、AddressBook、DeliveryAddress |
| shop | 营业状态、营业时间与配送政策 | Shop、OpeningStatus、配送规则 |
| catalog | 分类、菜品、口味、套餐、可售性与图片 | MenuProduct（DISH/SET_MEAL）、Category |
| cart | 选择商品、规格与数量、合并与清理 | ShoppingCart、CartItem |
| ordering | 下单、接单、拒单、取消、履约、再来一单、催单 | Order、OrderLine、金额及地址快照 |
| payment | 支付单、渠道回调、退款与对账 | Payment、Refund、PaymentGateway |
| notification | 来单/催单消息及投递跟踪 | Notification、DeliveryAttempt |
| reporting | 工作台、经营统计、销量与导出 | 专用查询模型与统计投影 |

模块内部按 domain/application/infrastructure/web 分层，对外通过 api/events 的命名接口。
跨模块只传契约和业务标识，不能映射其他模块的 JPA 实体或查询其业务表。

## 业务规则优先于参考实现

参考源码包含直接模拟支付成功、固定退款金额、直接修改订单状态等教学实现。本项目必须重新定义
并验证相应行为：服务端计价、订单不可变快照、状态机、资源归属检查、支付回调验签、请求幂等、
超时竞争和退款结果确认。参考中的字段和技术设计不自动成为本系统约束。

单店是当前业务边界；多店、库存预占、骑手平台和优惠券出现明确需求时单独分析。
账号模块只收集认证和账号管理所需资料，不把人事数据自动塞进身份聚合。

## 协作与事务

下单通过 customer/shop/catalog/cart 的公开契约校验资料、营业状态和价格，再在短事务内建立
订单及明细快照、结算相应购物车条目。需要版本校验，避免误删结算期间新加入的商品。

ordering 调用 payment 的公开 API 发起支付/退款意图，监听 payment 的结果事件；payment 只保存
业务引用，不反向导入 ordering 的类型，避免循环依赖。通知和统计消费事件，在各自事务中幂等处理。

业务更新与 Modulith JPA 事件登记共同提交或回滚。外部网络调用在短数据库事务之外执行，使用
持久化意图、幂等键、结果查询和补偿处理异常；支付和超时取消竞争不能使订单终态回退。

## 数据和查询

所有业务表从本项目新基线建立，不导入参考项目 SQL 或账号。统一使用 UUID 标识、UTC 时刻、
精确金额和显式状态。实体关系与外键限定在模块内，报表按需求使用投影和自己的读取模型。

常规存取使用派生查询；组合条件用 Specification；有可测量需求时才增加针对性的查询优化。
记录查询计划和索引依据，避免 N+1、无界分页及在控制器阶段懒加载。

## 测试与资源

领域测试验证行为与不变量；模块测试验证边界及契约；PostgreSQL/JPA 测试验证映射、锁与事务；
Redis 和对象存储使用隔离资源测试。发布前保留失败恢复、权限和日志脱敏检查。

现有基础设施已经就绪。支付宝沙箱应用、测试账号和通知地址在沙箱联调前准备，
设备平台与 SDK 的沙箱支持届时核对，详细说明见 [中间件清单](INFRASTRUCTURE.md)。
当前不因已有中间件而引入 Nacos、RocketMQ 或额外调度平台。后续阶段按用户指令推进。
