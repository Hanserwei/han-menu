# 移动端与支付决策

状态：产品方向已确定，P3 顾客后端与 P4 未支付订单已实现；支付接口仍为规划草案，尚未实现。日期：2026-09-19。

## 决策与范围

顾客移动端采用 Flutter 开发原生 App，不采用微信小程序。管理端继续使用独立后台，后端保持
Java 模块化单体，通过 `/api/v1`、Bearer、UUID、UTC 时间和 RFC 9457 错误协议服务客户端。

这是个人项目，支付仅使用支付宝沙箱测试，不以正式商户资质、生产支付或真实资金交易作为验收
前提。P3 已完成顾客身份、资料、地址簿与购物车，P4 已完成未支付订单；Flutter 工程和 P5 支付集成仍待后续阶段，也不生成
空的支付 Controller 或返回“支付成功”的占位实现。

## 顾客身份

P1 实现的是员工身份。Flutter 的顾客认证已在 P3 独立实现：顾客与员工主体、权限、令牌用途明确
区分，顾客不能凭员工端路径规则或混用会话获得权限。注册/登录方式已在 P3 确定，不依赖
微信 openid、微信 code 换取身份、短信供应商或支付宝账号作为应用登录身份。

P3 已选择手机号标识加密码的独立顾客认证，当前不核验号码归属，具体行为见 [P3 契约](P3_CONTRACT.md)。
顾客登录凭证由 App 安全存储；后端仍根据当前会话状态授权。App 重启、后台恢复和网络重试都应
通过 API 获取服务端状态，不能依赖本地页面保存的订单或支付结果。

## 后端支付职责

payment 拥有支付单、退款单、渠道交易引用、幂等记录及渠道结果。ordering 通过公开契约调用
payment，并消费支付结果事件；payment 不反向引用订单聚合。渠道配置和 SDK 位于基础设施层。

`PaymentGateway` 按真实用例预留以下能力，具体 Java 类型在 P5 实施时确定：

- 准备 App 支付调用参数：使用服务端确认的业务金额、支付单号和过期时间签名。
- 查询渠道交易：用于通知遗漏、App 恢复及结果不确定时的主动确认。
- 校验并解析异步通知：校验签名、应用/收款主体、交易号、金额和状态，输出领域可理解的结果。
- 关闭未完成交易：配合订单取消和支付超时处理，解决查单/关单竞争。
- 发起退款与查询退款结果：使用独立退款编号和幂等策略，不将受理等同于退款完成。

应用私钥不进入 Flutter、API 响应、日志或 Git。沙箱与任何未来的生产配置、凭证和数据必须
明确区分；P5 实施时只启用沙箱适配器。渠道不可用时返回明确错误或待确认状态，不切换为伪成功。

## 拟定 HTTP 契约

以下为后续实现预留的能力与候选路径，不属于当前 OpenAPI，也不会现在添加运行时接口。
操作授权、请求 DTO、稳定状态枚举及支付版本规则在 P5 实施前细化。

| 能力 | 候选接口 | 关键约束 |
| --- | --- | --- |
| 创建订单支付意图 | POST `/api/v1/orders/{orderId}/payments` | 顾客拥有订单；服务端计价；Idempotency-Key；返回支付标识、状态、过期时间及 App 调用参数 |
| 查询支付状态 | GET `/api/v1/payments/{paymentId}` | 只允许所属顾客或有权限的管理员；返回服务端确认状态 |
| 接收支付宝通知 | POST `/api/v1/payment-notifications/alipay` | 使用渠道签名认证，不要求顾客 Bearer；按官方通知协议响应 |
| 发起退款 | POST `/api/v1/payments/{paymentId}/refunds` | 授权业务流程触发；校验可退款金额、支付版本和幂等键，不开放任意顾客退款 |
| 查询退款 | GET `/api/v1/refunds/{refundId}` | 校验归属和权限，明确区分受理中与完成 |

幂等键与主体、用例和请求内容关联：同键同请求返回同一业务结果，同键不同内容返回冲突。
重试获取 App 调用参数时不得重复生成业务支付单，参数有效期与支付单状态由服务端控制。

创建支付不接受客户端自行决定的金额；退款也必须由业务规则批准。资源变更携带版本，渠道通知
则依据验签、唯一渠道标识和服务端条件更新处理幂等，不要求渠道提交本系统的客户端版本字段。

App 支付响应可包含渠道标识、调用类型和不透明的已签名订单参数；仅暴露当前必要字段，不将完整
SDK 对象或密钥材料透传给客户端。JSON API 使用统一协议，渠道通知是明确的外部协议适配边界。

## 支付闭环

1. Flutter 请求后端创建支付意图，后端验证归属、订单状态和金额，持久化意图并准备沙箱调用参数。
2. Flutter 使用参数调用支付宝 App 支付 SDK。具体插件或原生桥接方案在移动端阶段选择。
3. SDK 返回成功、取消或未知结果后，Flutter 查询后端。SDK 返回值只影响交互提示，不直接修改订单。
4. 后端验签通知，或主动查询渠道确认交易，再提交支付状态和 Modulith 结果事件。
5. ordering 消费支付结果，按订单状态机推进；迟到支付与超时取消冲突时进入明确的关闭或退款补偿流程。

数据库事务保持短小，渠道网络调用在事务之外完成。通知可重复、乱序或丢失，需要唯一约束、状态
迁移校验及补查；App 断网、被杀进程后仍能查询已保存的支付单恢复展示。

## 验收与准备

- 后端契约与领域验收：资源归属、服务端计价、幂等、签名校验、超时竞争、查询补偿与退款状态。
- 沙箱联调验收：支持的设备平台上，Flutter 调用沙箱、后端确认结果、订单推进及退款查询闭环。
- 不以生产支付作为完成条件；沙箱资源缺失时只标注沙箱联调待完成，不能称已完成联调。
- 当前不假定 iOS 与 Android 的沙箱能力相同，接入前核对官方支持和实际测试设备。

后续需要沙箱应用 ID、服务端签名私钥配置位置、支付宝沙箱验签配置、测试账号、可达通知地址和
目标设备平台。密钥仅放本地受保护配置或环境变量；资源准备见 [中间件说明](INFRASTRUCTURE.md)。
