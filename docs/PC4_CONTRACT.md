# PC-4：实时通知与阅读恢复

日期：2026-09-21。基于PC-1—PC-3继续实现管理端通知；本文P4指管理端PC-4，后端P4未支付订单阶段已完成。
沿用Vue 3、TypeScript、antdv-next、pnpm与既有视觉规范，没有新增业务运行依赖。

## 页面与交付范围

| 入口 | 行为 | 权限 |
| --- | --- | --- |
| 顶栏通知铃铛 | 待阅读提示点、跳转通知中心、连接状态 | ADMIN / STAFF |
| 全局订单提醒 | 新订单或顾客催单的上下文提示，点击打开权威订单详情 | ADMIN / STAFF |

没有请求系统桌面通知权限或自动播放声音，提醒使用现有主题上下文中的页面通知。

## 模块与连接生命周期

新增notifications模块，内部拆分协议校验、HTTP适配、独立运行器、Pinia状态适配、铃铛和页面。
app启动装配层监听经过/me验证的员工身份，建立或停止唯一运行器；路由切换不创建额外Socket。
公共代码不反向导入业务；notifications不导入ordering内部模型，通过路由与公共查询键失效协作。

原生WebSocket使用与当前页面同源的固定路径 `/api/v1/notifications/stream`，HTTPS页面自动使用WSS。
连接前POST `/api/v1/notifications/stream-tickets`，握手子协议为固定业务协议及 `ticket.<一次性票据>`。
票据不写URL、sessionStorage、localStorage、Pinia状态或日志；每次重连重新签发，绝不重用旧票据。
只有收到正确READY才标记连接成功，建立TCP连接或签票HTTP成功不能代替业务握手。

员工退出、令牌到期、改密、被停用及会话切换均停止Socket、HTTP补查、心跳、重连计时器与事件监听，
清空当前员工通知状态；统一会话桥的AbortSignal保证凭证撤销时同步清理。未完成的旧请求、旧Socket事件
和旧确认弹窗不会恢复前一账号状态。HMR也主动释放旧运行器，避免开发过程中叠加连接。

## 心跳、重连与HTTP恢复

- READY等待最多10秒；连接建立后每15秒发送文本ping，8秒内未获PONG关闭该连接并重新取票据。
- 断线退避约1、2、4、8、16、30秒，加最多500ms随机抖动；收到READY后重置。票据请求的Retry-After优先。
- 网络offline时关闭Socket并暂停连接重试，online后重新连接并补查；不假装连接仍在线。
- 全局HTTP补查在页面可见时每15秒、隐藏时每60秒执行，恢复可见立即同步。即使WebSocket失败，仍可读取和确认通知。
- 关闭码1008触发HTTP身份复验；由真实401撤销会话，不仅凭浏览器无法区分的网络错误猜测员工已退出。
- WebSocket帧只触发HTTP补查，不直接写入页面记录、读取游标或已读进度。重复／乱序帧不重复入库或重复显示。
- 错误只展示安全Problem信息，协议坏帧及异常对象不进入日志；未知数据停止游标前移，不伪装为无通知。

## 两种进度与有界页面

1. **已拉取游标 cursor：**只来自完整HTTP页面的nextCursor。运行器从已读下界与已验证读取位置逐页补齐到hasMore=false。
   每页验证递增连续序列、UUID、固定类型、时间、页大小和nextCursor；坏页整体拒绝。页间失败从最后成功位置重试。
2. **已读进度 receipt：**GET/PUT `/api/v1/notifications/receipt` 的sequence和version，完全以当前员工服务器状态为准。
   收到实时帧、后台补查完成、打开通知页面、查看订单及服务器投递成功，都不自动PUT已读。

后台同步不缓存全部历史通知，只保留读取游标与最后提示。页面每次读取最多50条，历史翻页仅保存游标栈，
没有虚构总页数或全店未读总数。铃铛提示点仅表示已由HTTP验证的记录中有sequence高于已读下界的内容。
冷启动积压只点亮提示，不连续弹出历史消息；后续新事件合并更新一个提醒卡片，并使订单列表／工作台查询失效。

通知中心当前页面保持稳定。新消息到达时提示刷新，不把新条目偷偷纳入正在确认的范围。
默认待阅读页从receipt.sequence开始，确认框明确列出本页条数，PUT只提交该连续页末游标与当前receipt.version。
成功后再读取下一页；首50条确认不能自动推进到后台已补查的第55条。历史模式没有已读确认按钮。
一次点击订单只打开订单详情，不单独跳读某条记录。

## 多设备与结果未知

- 响应按receipt.version合并；迟到GET不能覆盖较新PUT或其他设备已经推进的进度，序号不能倒退。
- 另一设备改变已读下界时，当前页面保留并提示重新读取，不静默确认新范围。
- 确认发生409时只同步服务器进度，不自动再次PUT；新页面由员工重新检查后明确确认。
- 响应丢失时也先重读进度，避免原命令可能已成功时重复确认后续消息。
- 确认与提交期间禁止翻页、切换通知视图、跳转订单；会话失效时允许安全退出并销毁确认框。
- 首次同步未完成显示加载，失败显示错误；没有阅读状态时显示进度未知，不伪造“全未读”或“全已读”。

## 开发及部署Origin

Vite已代理HTTP及WS，但changeOrigin只改变代理Host，不会把浏览器Origin自动变为后端Origin。
后端必须显式允许实际的前端开发来源，例如：

```bash
NOTIFICATION_ALLOWED_ORIGINS=http://127.0.0.1:5173 ./scripts/with-env.sh ./mvnw spring-boot:run
```

也可将精确Origin保存在被忽略的根.env；使用localhost时需填写实际localhost来源。环境文件中的同名设置优先，
不要配置通配符。生产使用HTTPS/WSS，同源反向代理保留WebSocket升级头，并按实际公开Origin配置后端允许列表。
不提供跨站绕过、URL令牌或代理伪造Origin的兼容逻辑。配置不符时实时连接不可用，但界面可使用HTTP补查并显示状态。
