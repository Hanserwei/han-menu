# PC-2：经营基础资料管理

日期：2026-09-20。基于 PC-1 身份、请求、主题和权限基础，完成管理员经营资料页面；Flutter 继续暂缓。

## 页面与交付范围

| 页面 | 前端路由 | 本阶段功能 |
| --- | --- | --- |
| 员工管理 | /settings/employees | 姓名筛选、分页、新增普通员工、编辑资料、启停用；管理员不可停用 |
| 顾客管理 | /customers；/customers/:id | 名称／完整手机号／状态／注册日期筛选，分页、详情与启停用 |
| 分类管理 | /catalog/categories | 新建、编辑、排序号、启停用、无引用删除 |
| 菜品管理 | /catalog/dishes | 分类分页、图片／名称／价格／状态、上下架、无引用删除 |
| 套餐管理 | /catalog/meals | 分类分页、上下架与删除，组成菜品及固定规格 |
| 菜品／套餐编辑 | /catalog/{dishes,meals}/new；/:id/edit | 独立编辑页、资料校验、图片关联、规格／套餐组成、草稿保护 |
| 门店设置 | /settings/shop | 单店名称／电话／地址维护，开店与打烊，顶栏及工作台联动刷新 |

上述页面仅允许 ADMIN。STAFF 菜单中隐藏，直接 URL 由路由守卫拒绝，服务端继续复验当前员工权限。
目录父菜单展开菜品、套餐、分类；系统管理开放门店与员工；顾客页支持直接访问详情。
订单中心、关联订单跳转、通知与 WebSocket、支付／退款流水、报表与审计仍按后续阶段推进。
本阶段不增加顾客代改资料／密码、任意退款、库存、营销或多店功能。

## 交互与业务约束

### 员工、顾客与门店

员工新建固定 STAFF，输入用户名、姓名、可选电话及初始密码；编辑不显示角色和密码变更入口。
员工状态使用 ACTIVE/DISABLED；顾客状态使用 enabled 布尔值；门店状态使用 OPEN/CLOSED，不能互用模型。
启停用明确提示会话失效，真实服务器结果返回后才更新界面；重新启用不恢复旧令牌。

顾客详情默认掩码手机号，主动展开才显示完整值；列表不暴露地址簿或购物车。顾客和员工筛选姓名／电话
仅保存在页面内存，查询键采用临时作用域与筛选修订号，不把个人筛选值写入 URL 或查询键；离页不长期保留列表缓存。
顾客注册日期按上海时区转换为左闭右开的 UTC 区间，不采用报表包含首尾日期的语义。

门店资料保存与营业状态分开。存在未保存草稿时，先保存或放弃，再开店／打烊；资料不完整开店由服务器拒绝。
状态变更后刷新 storefront/workspace，未自动保存未提交的联系资料。

### 商品与分类

商品列表仅使用 kind/categoryId/page/size，不虚构名称、状态搜索或批量操作。后台默认每页20，可选50，
界面1基页码转换为后端0基。表格使用数据库总量；删除末页最后一条时回到上一页。

分类创建后种类固定；排序号0—10000，名称最多50字。删除、停用与商品引用冲突保留服务器的明确提示。
分类为后端有界完整数组，不做伪服务端分页。所有有版本资源的写操作提交服务器当前 version。

商品新建保存后默认下架；在售商品必须显式下架后再进入编辑。不把下架／编辑／再上架合并为隐式操作。
价格先校验十进制文本，范围0.01—999999.99、最多两位小数，不静默舍入、不在前端重新计算订单金额。
下架、删除、编辑仍以服务端套餐引用规则为准，前端不绕过也不编造反向引用列表。

菜品口味最多10组，每组1—20个选项，名称与选项去空白后不能重复，每组单选，可标必选。
套餐使用分类＋分页菜品选择器；最多50个不重复菜品，每项数量1—99，固定口味必选项不能漏填，不能嵌套套餐。
编辑既有套餐时有界读取组成菜品的当前规格；查询失败禁止保存失去约束的组合。商品详情草稿与查询缓存深度分离。

### 图片

Upload 选择 PNG/JPEG，本地预检5MiB、边长4096、总像素1600万；服务端继续验证真实内容。
上传使用统一认证客户端的 multipart 序列化，浏览器生成 boundary；成功取得 imageId 后再保存商品关联。
上传期间禁止保存与离开，失败保留草稿，可重选。图片预览使用短期签名 URL，不附加员工 Bearer；
URL 失效提供“刷新图片”重新申请。移除关联清空 imageId，不删除共享存储对象。

## 并发、故障与资源生命周期

- 复用统一 useCommand 处理提交中状态及确认；不自动重试写请求、不提前展示成功。
- 409、服务器异常或网络结果未知保留草稿，禁用重复提交，要求显式重新读取；重新读取有未保存确认。
- 关闭抽屉、离开路由、同编辑路由换参数和关闭浏览器均保护草稿；认证失效时允许安全退出。
- 异步详情切换或卸载后忽略旧请求结果。图片上传还检查当前员工会话代数，不能污染后来账号。
- 列表加载、筛选空结果、读取失败有独立反馈；读取失败不假装零数据。
- Employee 更新204后重新读取列表，其他接口使用服务端返回的新快照；不自行推断 version + 1。

## 后端 OpenAPI 修正

实践发现三个控制器内的同名 StatusChange 被文档生成器合并成门店状态模型。
将内部请求类型明确改为 EmployeeStatusChange、CustomerStatusChange、ShopStatusChange，HTTP 路径、JSON 字段、
业务规则和权限均不变。补充真实 OpenAPI 集成断言，重新抓取契约并生成 TypeScript 类型；没有用 any 或关闭类型检查绕过错误。
本次没有数据库结构或业务状态机变更，无需新增 Flyway 迁移。
